# Startup Cadence

> Category: execution — Task automation, command running, and process management

## Description

Enforce the Patricia-approved startup/shutdown cadence. Always sync first, probe second, APIs third, work last. Never pull a model before checking API keys.

## Instructions

# Startup Cadence Skill (Patricia v2)

This is the mandatory operational rhythm for every Mortimer Mobile session. Execute or explain why not.

## STARTUP (first 60 seconds of any session)

```
1. PRE-FLIGHT   → Are sync token, termux-api, ollama, git online?
2. SYNC PULL    → Get latest state from GitHub BEFORE doing work
3. STATUS PROBE → Memory, disk, battery, versions snapshot
4. API INVENTORY → Check OpenRouter, DeepSeek Pro, any new keys
5. VPS INVENTORY → What models/skills/workflows are on the VPS?
6. LOCAL MODELS  → What's available locally? Disk usage?
7. MEMORY FILE   → Create today's MD if missing (YYYY-MM-DD.md)
8. FINAL INVENTORY → Skills loaded, project files present
```

## RULES (non-negotiable)

1. **Sync before work** — never make changes before pulling latest state
2. **APIs before pulls** — check OpenRouter/DeepSeek keys before downloading any local model
3. **Memory every session** — create today's .md file. Log decisions, state changes, work done
4. **VPS awareness** — know what's on the VPS before duplicating work locally
5. **No silent failures** — if a step fails, flag it. Don't hide errors with 2>/dev/null without logging

## SHUTDOWN (last 30 seconds)

```
1. UPDATE MEMORY → Append end time, decisions, state to today's MD
2. STATUS SNAPSHOT → Final system probe
3. SYNC PUSH → Upload everything to GitHub
```

## WHEN TO USE
- Every session start (auto-loaded by .bashrc via ~/aios_features/startup.sh)
- Every session end (run `shutdown`)
- After major state changes (new skills, models pulled, configs changed)

## Jurisdiction

**Startup Cadence governs SESSION-LEVEL lifecycle only.** This includes: startup pre-flight, sync pull/push, status probes, API/VPS inventory, memory file creation, session shutdown.

**Startup Cadence does NOT govern project rhythm.** Project check-ins, sprint reviews, agent workflow scheduling, business venture tracking — these are the domain of **Cadence**, a separate skill that handles all non-session operational tempo.

**Precedence**: Startup Cadence takes precedence for session lifecycle. Cadence governs everything else.

**Coexistence**: These skills are designed to coexist. Think of it as:
- **Startup Cadence** = the engine (keeps the machine running)
- **Cadence** = the GPS (keeps projects on route)
